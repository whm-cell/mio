# Mio 万联 OneLink 第三方登录 PRD

**待评审 · 2026-11-25**　由产品、研发和万联接口负责人核对。本期交付范围涵盖 Mio 后端与 `mio-admin-web` 管理端（含全局配置与万联登录验证沙箱）；`miioo` 用户端为后续消费方，不在本期改造。

## 1. 摘要

用户从 Mio 发起万联授权，返回后可直接进入已绑定的原 Mio 账号，或明确选择创建一个暂未绑定手机号的新账号，或在已有已验证手机号账号上关联万联。已登录 C 端用户也可在近期会话内主动绑定万联。管理员在 `mio-admin-web` 按环境维护万联运行期热开关（默认关闭）、预期 `client_id` 与客户端注册，并在专用「万联登录验证沙箱」页面内完成全部 C 端路径的同浏览器真实闭环验证。

**成功判据**　同一老用户分别用原手机号和万联登录，Mio 返回同一个 `userId`，读取同一个原有项目或资产；首次使用者自主决定账号归属；未开启热开关时入口安全关闭，且 `mio-admin-web` 管理端配置与验证沙箱可独立完成端到端验收，无需改动 `miioo`。

## 3. 依据及当前系统

- **万联文档。**《接入router测试环境登录功能》定义了 Router 的加密跳转、成功及拒绝回调、客户端注册和刷新。《desk-router登录》给出兼容的 JavaScript 加密示例。`register` 定义应用身份，日常登录通过 `/authorize?enc=…` 发起。
- **2026-11-24 测试环境实测与 2026-11-25 业务确认。** 实测请求使用 `clientName="miioo"`、展示名 `Miioo` 和 `clientType="web"`。用户同意后浏览器收到 `access_token`、`refresh_token`，访问令牌 payload 解码得 `client_id="miiooClientId"`，其字符串 `sub` 与同次 Router 用户资料 `userId` 一致；Router 自身登录产生的 `routerClientId` 属于中间步骤。样本不含手机号声明，勾选授权手机号不能替代 Mio 的手机号验证。2026-11-25 已确认：`miioo` 为万联可信客户端身份，`sub` 作为万联用户级稳定唯一标识；v1 采用 Base64URL 解析 JWT payload 提取 `sub`，不做加密验签或出站自省，并配合按环境默认关闭的热开关控制暴露面。
- **Mio 后端基线。** Better Auth 已管理 `user`、`account`、会话 Cookie 和禁用账号。手机号可空且唯一。现有匿名 `phone-number/verify` 遇到新号码会自动建号，不能直接用于“绑定已有账号”。已登录用户的手机号绑定要求近期会话（10 分钟内）和空闲号码，并遵循全局短信模式策略。管理后台全局配置已通过 `src/plugin.ts` 向认证域注入只读策略快照，满足 `src/auth` 不直接导入 `src/admin` 的模块边界。[认证底座](../../auth.md) · [认证 HTTP 契约](../../apis/auth.md) · [已接受的手机与微信能力](../ai-drama-foundation/complete/report.md#phone-wechat-auth)
- **管理端与前端基线。** `mio-admin-web` 的「全局配置」已承载邮箱密码开关与短信模式策略，通过独立管理员 Cookie `mio.admin_session`（`Path=/api/v1/admin`）鉴权，并已将 `/api/*` 同源代理至 `mio` 后端；C 端登录会话 Cookie `mio.session_token`（HTTPS 为 `__Secure-mio.session_token`，`Path=/`）与管理员 Cookie 路径及名称相互隔离，支持在同一浏览器内保留管理员登录的同时验证全部 C 端登录与绑定路径。`miioo` 前端仓库由前端团队独立维护，本期不纳入改造。[管理端契约](../../apis/admin.md) · [已接受的后台全局配置](../web-admin-console/complete/report.md#admin-global-settings)

## 4. 产品目标与范围

**本期范围**　交付按环境服务端配置、管理端运行期热开关（默认关闭）与客户端注册、万联 Web 授权发起与回调解析、首次账号选择（创建新账号或绑定已有已验证手机号账号）、已登录 C 端会话显式绑定、原有手机号/微信/邮箱登录兼容，以及 `mio-admin-web` 的「全局配置 → 万联登录」配置区和「万联登录验证沙箱」专用验证页面。

**本期非目标**

- **不修改 `miioo` 前端**：不改动 `miioo` 的登录弹窗、个人中心或旧认证 API；`miioo` 作为后续消费方在后端契约与沙箱验收完成后独立对接。
- **不做跨账号合并**：这里的“绑定已有账号”只给目标 Mio 账号增加万联登录方式；两个已存在 Mio 用户之间的人员或资产合并另行处理。
- **不持久化或续期万联令牌**：本期仅将万联授权用于登录与显式绑定，Mio 会话采用现行期限与撤销机制，不长期保存万联令牌。原文档非 30 天免登录模式为访问令牌 2 小时、刷新令牌 24 小时，30 天免登录不支持续期，且刷新接口 `clientType` 仅列 `router`/`desk`；若未来需代用户调用万联再单独评审续期与保管。
- **v1 不做 JWT 密码学验签或出站令牌自省**：具体解析规则与诚实安全边界声明见第 7.2 节。

**验收目标**　上线或环境验收须取得三类结果：第一，四条 C 端路径均可从 `mio-admin-web` 验证沙箱与真实万联测试环境走通至预期 Mio 身份；第二，重复提交、绑定冲突、用户拒绝、非法/过期/中间态令牌及未开启热开关场景产生的额外人员或跨用户关联数均为零；第三，管理员在「全局配置 → 万联登录」可查看环境就绪度、控制热开关、调整预期 `client_id` 并执行注册，普通用户无权访问管理接口。具体观测项见第 8.3 节。

## 5. 用户路径与界面

本期四条 C 端路径均在 `mio-admin-web` 新增的独立菜单页 **「万联登录验证沙箱」** 中完成真实浏览器端到端验证（同浏览器下管理会话与 C 端会话 Cookie 隔离，经 `/api/*` 同源代理调用 Mio 认证接口）。沙箱同时提供当前 C 端会话状态面板（调用 `/api/v1/me` 与 `/api/v1/me/profile` 展示 `userId`、`phoneNumber`、`onelinkBound`）与 C 端退出按钮（`/api/auth/sign-out`）。后续 `miioo` 登录页与个人中心直接复用同一套后端契约。

| 场景                          | 用户/验证者在沙箱中看见什么、怎么操作                                                                                                                | 完成后的结果                                                                                                       |
| ----------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| 曾经绑定，当前未登录          | 在沙箱 C 端未登录态点「使用万联登录」，跳转万联完成授权并返回。                                                                                      | 找到已绑定且未禁用的 Mio 用户，签发本站 C 端会话，`/api/v1/me` 返回原 `userId`，`onelinkBound=true`。              |
| 首次授权，选择新账号          | 回调后沙箱并列展示「创建新账号」和「绑定已有 Mio 账号」。点「创建新账号」进入新会话，并可选择通过现行 `/api/auth/phone-binding/*` 补绑空闲手机号。   | 事务创建一条人员记录与一条万联关联，初始手机号为空。补绑空闲手机号通过短信验证码核验后，手机号与万联登录同一账号。 |
| 首次授权，已有手机号账号      | 回调后选「绑定已有 Mio 账号」，输入原手机号，触发专用短信验证码，输入验证码并显式提交绑定。                                                          | 关联写入已验证且未禁用的原账号，签发原账号会话并保有原有数据；号码未对应可绑定原账号时拒绝且不建新号，可重输或改选 |
| 已登录 C 端会话，主动绑定万联 | 先在沙箱确认已登录且为 10 分钟内创建的 C 端会话，点「绑定当前账号」跳转万联授权；返回后核对沙箱展示的待绑「万联账号 ID」，点击「确认绑定」显式提交。 | 确认成功后 `/api/v1/me/profile` 展示 `onelinkBound=true`。取消、C 端退出或切换账号时保留原有归属，不写入新关联。   |

用户点「拒绝」或关闭万联授权页时保留进入前的账号关系；未完成的待处理操作到期后可重新发起。手机号已被另一账号使用、万联身份已属于他人或当前用户已绑另一万联身份时，页面统一提示「该登录方式已绑定，暂不能完成本次操作」，保留原归属。已创建独立新账号的用户后续补绑被占用手机号时同样返回冲突提示，不自动搬移数据。

## 6. 人员与绑定数据

Mio 的 `user.id` 是人员和业务资源的归属键。在 Better Auth 的 `account` 中新增 `providerId="onelink"` 的记录，`userId` 指向该人员。`accountId` 按 2026-11-25 确认采用解析校验通过的非空字符串 `sub`（万联用户级稳定唯一标识），测试与生产环境通过独立数据库与配置隔离。若未来万联调整 `sub` 命名范围或跨环境迁移，须先核对旧绑定映射再切换。

| 数据                       | 用途与约束                                                                                                                                                                                                                                                                         |
| -------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 万联 SSO 配置与登记        | 新增管理域配置表（如 `mio_admin_onelink_sso_config`），按环境记录运行期热开关 `enabled`（默认 `false`）、可信登记状态、`clientName="miioo"`、已保存/预期 `clientId`、乐观锁 `revision`、最近注册结果与操作审计信息。服务端 `enc` AES-256-GCM 密钥与万联地址严格走 `.env`，不入库。 |
| 人员与第三方账号           | 复用 `(providerId, accountId)`、`(userId, providerId)` 两项唯一约束。新用户沿用现有建人逻辑自动分配 `displayId`，手机号留空，占位邮箱使用保留域且 `emailVerified=false`。昵称、手机号文本、实名信息与上游令牌不承担关联键职责。                                                    |
| 站内待处理操作与待绑定身份 | 在认证库记录短时待处理操作（用途 `login`/`bind`、有效期，绑定另记发起 `userId` 和 `sessionId`），浏览器仅持有短时 HttpOnly 待处理 Cookie。回调解析通过且需要用户选择或确认时才暂存待绑候选；完成、取消或过期后失效。                                                               |
| 事务与重试                 | 新建人员和万联关联同事务提交。绑定已有账号和绑定当前账号均原子核验归属、消费待处理操作并写入关联。唯一约束冲突后保留原归属不覆盖。登录路径在写入成功后签发 Mio 会话，当前会话绑定沿用原会话；已完成操作重复提交不再重复建人、写关联或重新签发会话。                                |

## 7. 功能与接口实施

下述路由名称、字段与边界供团队核对与分单元实施。各单元实现时同步更新现行规范：单元 ① 更新 `docs/apis/admin.md` 并新增 `docs/integrations/onelink-sso.md`（登记于[集成契约目录](../../integrations/index.md)）；单元 ③ 更新 `docs/auth.md` 与 `docs/apis/auth.md`。后端代码分别归属[管理路由](../../../src/admin/http.ts)、[插件装配](../../../src/plugin.ts)、[认证路由](../../../src/auth/http.ts)、[短信验证](../../../src/auth/phone.ts)与[用户资料](../../../src/auth/account.ts)，并严格遵守 `src/auth` 不导入 `src/admin`（由 `src/plugin.ts` 注入窄只读快照读取器）。本期前端改动全部落在 `mio-admin-web`（全局配置万联卡片、验证沙箱页及 `mio-admin-web/vite.config.ts` 穿透主机配置），不改 `miioo`。

### 7.1 管理员配置、热开关与客户端注册

在 `mio-admin-web` 的 **全局配置 → 万联登录** 展示当前环境标识、服务端 `.env` 配置就绪度（`enc` 密钥与万联授权/注册地址是否齐备，绝不回传密钥明文）、运行期热开关 `enabled`（默认 `false`）、可信客户端登记状态（`miioo`）、预期 `client_id` 配置，以及独立「注册万联客户端」按钮。页面打开仅读取状态；管理员显式操作后由后端校验 `mio.admin_session` Cookie 与允许的 `Origin`。

`POST /api/v1/admin/onelink/sso/register` 固定向本环境配置的注册地址（测试环境为 `POST https://api-test.wanlian.cloud/sso/client/register`）发送 `{"clientName":"miioo"}`，执行中禁用重复提交。由于万联已确认 `miioo` 为可信客户端身份（2026-11-24 测试样本携带 `client_id="miiooClientId"`），注册结果简化处理，不设复杂的多态 `362` 人工对账流程：

| 万联结果                                      | 后端行为及管理员反馈                                                                                                                           |
| --------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| HTTP 成功且业务码 `200`                       | 校验非空 `data.clientId`，保存 `clientId` 与可信已登记状态并记录脱敏审计，界面展示「已注册」及 ID。是否对外开放仍由热开关 `enabled` 独立控制。 |
| `362` 客户端已存在                            | 不阻塞；保留本地已有 `clientId`，若本地尚无记录则按已确认的 `miioo` / 已配置预期 `clientId` 标记为可信已登记并记录脱敏审计。                   |
| `363`、`364`                                  | 对应提示名称含空格或万联客户端模板缺失，向管理员返回脱敏错误与 `traceId` 便于定位。                                                            |
| 超时、HTTP/业务错误、响应缺字段、本地保存失败 | 保留原有可用配置与登记状态，返回脱敏失败提示；审计与日志仅保留操作、环境、业务码与 `traceId`，不记录任何密钥或原始凭据。                       |

管理员可通过 `PATCH /api/v1/admin/onelink/sso` 在线热更新 `enabled` 开关与预期 `clientId`，须携带乐观锁 `expectedRevision`（版本冲突返回 `409 SETTINGS_CONFLICT`）并写入脱敏审计日志；提交成功后立即刷新经 `src/plugin.ts` 注入到认证域的内存只读快照，无需重启服务。

### 7.2 发起授权、回调解析与安全边界

1. **发起授权（`POST /api/auth/onelink/start`）。** 先核对运行期热开关 `enabled === true` 且服务端 `.env` 配置就绪（关闭或未配置时返回不可用）。输入 `intent="login"` 或 `"bind"`。当 `intent="bind"` 时，要求当前浏览器持有创建时间不足 10 分钟且未撤销、未禁用的 C 端会话，并记录发起 `userId` 与 `sessionId`。服务端写入短时待处理记录并下发 HttpOnly 待处理 Cookie。
2. **加密构造授权地址。** 明文 JSON 仅包含万联文档规定的六个字段：`clientType="web"`、`clientName="miioo"`、`name="Miioo"`、`url`（`MIO_AUTH_BASE_URL` 对应的本站 origin）、`callback`（`${MIO_AUTH_BASE_URL}/api/auth/callback/onelink` 固定 HTTPS 回调地址）和 `timestamp`（毫秒时间戳）。后端使用严格来自服务端 `.env` 的 32 位 ASCII 字符 UTF-8 密钥（绝不写入仓库、PRD 或前端构建产物）执行 AES-256-GCM 加密，12 字节随机 IV、16 字节认证标签，分别 Base64 编码后拼为 `iv:authTag:ciphertext` 并整体 URL 编码，返回 `{url}`（测试环境前缀 `https://scenic.wanlian.cloud/authorize?enc=…`）。
3. **回调接收与 v1 令牌解析（`GET /api/auth/callback/onelink`）。** 先检查热开关启用状态与本站有效待处理 Cookie/记录（绑定用途还须校验当前浏览器会话仍属于原 `userId`/`sessionId`）。收到 `unauthorized=true` 按用户拒绝收敛并重定向。成功时读取 `access_token`（本期不持久保存 `refresh_token`）；按 2026-11-25 确认，**v1 不执行 JWT 密码学验签，也不发起万联令牌状态/自省出站请求**，而是执行以下结构与语义校验：
   - 校验 `access_token` 为标准 3 段点分 JWT，对 payload 段做严格 Base64URL 解码并解析为 JSON 对象；
   - 要求 `sub` 为非空、不含控制字符的字符串（作为万联用户级稳定唯一标识）；
   - 若存在数值型 `exp`，校验当前时间未超过过期时间，过期即拒绝；
   - 显式拒绝 Router 中间态令牌 `client_id === "routerClientId"`；
   - 若 payload 存在 `client_id`，须命中本环境已配置/可信客户端标识集合（如 `"miioo"` / `"miiooClientId"`）。

   任一校验不通过立即终止此次操作并跳转脱敏错误态。

4. **分流与干净重定向。**
   - `login` 且该 `sub` 已绑定未禁用 Mio 用户：签发本站 C 端会话 Cookie，消费待处理记录并 `303` 重定向至干净结果路径（被禁用账号拒绝签发）。
   - `login` 且尚未绑定：暂存已解析的待绑候选，不创建人员也不写永久关联，`303` 重定向至干净账号选择路径。
   - `bind`：只暂存已解析的待绑候选，**此 GET 绝不写入永久绑定**，`303` 重定向至干净绑定确认路径。
   - 所有回调响应统一携带 `Cache-Control: no-store` 与 `Referrer-Policy: no-referrer`，目标 URL 不带上游令牌或 `sub`；网关、应用日志与埋点略去回调查询串，浏览器本地存储不保存上游令牌。

> **安全边界声明（必读）**
>
> 1. **仅解析 JWT Payload 的伪造风险**：按 2026-11-25 确认，v1 仅以 Base64URL 解码 JWT payload 并检查结构、`sub`、`exp` 与 `client_id`，**不进行密码学签名验证，也不向万联在线查询令牌有效性**。该实现**无法防御**直接暴露于不可信公网流量下的恶意客户端伪造三段式 JWT（任意构造 `sub` 与未来 `exp`）请求回调接口。因此，万联登录在管理端默认关闭（`enabled: false`），v1 仅适用于受控开发、测试与验证沙箱；若未来面向公网生产开放，须补充万联正式验签/在线自省能力，或在明确评估风险后通过按环境热开关严格控制开放范围。
> 2. **无协议往返标识的来源边界**：万联文档回调不含可独立证明令牌属于同一次点击的 `state` 字段。已登录显式绑定依赖本站原近期会话展示待绑候选（仅取得 `sub` 时标为「万联账号 ID」）并由用户点击确认；确认提交锁定页面展示的候选标识，后到回调不能静默替换当前候选，但前端确认不能改变上游回调缺少点击绑定证明的协议事实。

### 7.3 手机号验证、接口清单与管理端验证沙箱

已有手机号账号绑定分支在提交前须经专用短信验证码核验：在 `smsMode='live'` 下挑战独立绑定当前待处理操作、规范化大陆手机号与发起浏览器，使用真实短信运行时与持久短信预算；当管理员在后台将全局配置切换为高风险的 `smsMode='bypass'`（固定 6 位验证码）时，同步跳过真实短信下发与持久预算、以恒定时间比对后台 6 位固定码（仅限受控开发／测试环境，严禁公开生产长期开启）。两种模式均不暴露手机号是否已注册；验证时仅查找**已存在、已验证且未禁用**的 Mio 用户，绝不自动建号。
