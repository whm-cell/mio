2026-11-13，项目负责人明确要求按推荐方案开始实施手机号验证码和微信认证。沿用已有邮箱密码、Better Auth 用户与 PostgreSQL 会话；用户以任一方式登录后仍由同一 `userId` 表示。实现、真实供应商验证和用户接受分别判断，目前尚未形成新的接受结论。[原方案](../../pending/auth-extension.md)保留背景与取舍。

## 本期范围和安排

- **A1 手机号**：大陆手机号规范为 E.164；验证码可自助注册或登录，已有账号可以在近期可信会话下首次绑定空闲号码。验证码用途、号码及绑定时的用户和发起会话须对应；已占用号码不能转移或合并账号。保留邮箱密码及现有会话安全。
- **A2 微信**：网站应用登录及当前用户显式绑定微信。微信可独立登录，手机号绑定可选；服务端完成授权交换并校验发起浏览器、state 和原会话，禁止同邮箱自动合并。AppID、回调环境和真实供应商验收各自核实，缺证不阻断已授权实现。
- 两单元在同一认证成果中衔接：先实施 A1 和共享认证迁移，再实施 A2；每个单元均须对其真实入口、失败与权限边界取证，再由项目负责人接受。开发准备、实现候选和真实接受不是同一结论。

手机号密码与找回、手机号或微信换绑／解绑、账号自动合并、旧用户／资产／会话迁移、前端改造、生产部署均不属于本期。

## 实现约束

短信短期挑战和费用预算分开存储在 PostgreSQL。验证码按用途和请求上下文绑定，校验与单次消费由数据库串行化；调用认证库创建用户或会话发生在消费之后，若后续失败验证码不会恢复，需重新请求。短信提交前先占预算，供应商明确受理后才激活该挑战；拒绝、超时或未知结果不自动重试且不返还预算。现有 Redis 请求限流及其 65 秒恢复语义不用于恢复每日短信预算。

固定版短信 SDK 默认跟随重定向，独立单连接约束用于阻止验证码正文被再次发送；固定目标直连和代理边界见短信契约。

固定版微信 provider 默认优先 unionid、缺失时回退 openid，可能因资料变化切换主体；本期固定为 AppID/openid，AppID 变化须先迁移。库的数据库 state 读取与删除分离，增加基于签名 state Cookie 的单次保留栅栏；库只检查发起会话仍存活，额外比较回调当前会话，避免切换用户后误绑定。两项均沿库的公开插件扩展点，不另建 OAuth 框架。数据库复合唯一索引阻止并发时的重复归属；`(userId, providerId)` 同时约束现有 credential，迁移时若发现重复须人工对账。

微信绑定保留库在回调阶段的权威会话核验时点，本期不增加提交时与并发撤销的原子化约束。

固定版 provider 的两次微信请求缺少可配置的完整期限，资料请求默认跟随重定向；仅替换这两次固定目标出站调用，保留库的授权 URL、state、账号与会话路径。5 秒中止和 32 KiB 上限约束故障占用，失败不重试；这些保护增加一处窄适配器和针对性测试，避免把无响应或重定向当作登录成功。

现行契约由[认证底座](../../../../auth.md)和[认证 HTTP 契约](../../../../apis/auth.md)维护；未验证的供应商行为和既有认证成果分别保留原有证据边界。
