## HTTP 与状态边界

- `POST /api/auth/wechat/qr-session` 创建 5 分钟会话；可选 `callbackURL` 仅接受当前固定 `MIO_AUTH_BASE_URL` 下的相对路径，缺省 `/auth/wechat/qr-complete`。成功为 201，返回 `qrcode_id`、`authorization_url`、`expire_seconds: 300`，并设置短期 QR state Cookie。创建限额为每 60 秒 20 次。
- `GET /api/auth/wechat/qr-session/{qrcode_id}/poll` 使用 QR state Cookie；支持 `pending`、`confirmed`、`failed`、`expired`、`consumed`，不承诺无法可靠观察的 `scanned`。未知 ID 为 404，QR Cookie 缺失或错配为 400，未启用微信为 503。轮询限额为每 60 秒 300 次，客户端建议每秒一次且过期后停止。
- 首次 `confirmed` 要求当前浏览器已有有效 Mio Session，且可信用户与该 QR 会话确认用户一致；在数据库行锁下读取并转为 `consumed`。身份不满足时不得消费或透露登录结果。轮询只返回状态，确认后由现有 `/api/v1/me` 读取身份。
- OAuth callback 继续由 Better Auth 校验 state 与发起 Cookie、查询或创建账号、创建 Session 并向同一浏览器写入 Cookie；QR bridge 仅关联对应 QR 会话。成功、失败、重复和并发 callback 不得重复创建或替换该 QR 登录结果，供应商失败保持脱敏。
- 同一浏览器必须打开 `authorization_url` 的微信授权页面；它不是普通二维码图片 URL。本期不实现手机直接回调服务端后向电脑交接凭据的另一种跨设备 state 模型。现有普通微信登录与首次绑定入口保持其原有职责。
- 沿用现有 Origin、JSON、16 KiB、10 秒读取期限、HttpOnly／SameSite=Lax／HTTPS Secure Cookie、固定 BASE_URL 和 `Cache-Control: no-store` 规则；未知路径不交给 Better Auth，服务凭据不能成为用户身份。

## 持久化与迁移

认证 PostgreSQL 的 QR 表保存不透明 QR ID、OAuth state 摘要、QR Cookie 摘要、状态、确认用户、确认与过期时间、脱敏失败原因码；QR 表不保存 state、Cookie、Session secret 或 OAuth token 的明文。Better Auth 自身的数据库 OAuth state 继续沿用原策略，不受这条 QR 表规则替代。对 state、过期时间及状态的查找建立适当索引，创建时有上限地清理过期记录，不增加常驻清理 Worker。

QR 模型与迁移进入同一认证结构来源，由 `auth:migrate` 显式应用并在启动时核对，运行时不自动建表。复用[PostgreSQL 契约](../../../../integrations/postgres.md)和认证池生命周期；破坏性自动回归只使用本轮权限隔离 schema，不能触碰业务库。

## 验收与规范归属

验收覆盖 HTTP 来源／方法／正文／Cookie／缓存／禁用微信与未知路径，全部状态与错误 Cookie、跨浏览器、callback 重放和并发、poll 并发、账号唯一归属与不自动合并、Session identity 一致性、迁移／启动检查／有界清理／事务失败，以及原认证、打包和卸载回归。

真实验收须在获授权的微信网站应用中观察电脑主页面、授权窗口、手机扫码、callback 域名、Cookie、过期与重复扫码，并绑定实际候选及契约修订。替身、静态检查和打包装载证据各自报告，均不能代替真实扫码或生产验证。

必要配置与迁移行为归[认证底座](../../../../auth.md)，实际路由、错误和限流归[认证 HTTP 契约](../../../../apis/auth.md)，微信浏览器、provider 和回调约束归[微信契约](../../../../integrations/wechat.md)。这些现行规范须在 verify 前与实际实现对账并进入受验候选；原接受事实继续由所属成果入口维护。
