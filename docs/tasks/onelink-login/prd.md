# Mio 万联 OneLink 第三方登录 PRD

**待评审 · 2026-11-24**　由产品、研发和万联接口负责人核对。适用于 Mio 后端、miioo Web 用户端和 mio-admin-web 管理端。

## 1. 摘要

用户从 Mio 跳转到万联授权，回来后可以进入原来的 Mio 账号，或明确选择创建一个暂未绑定手机号的新账号。已登录用户也可以在个人中心主动绑定万联。管理员在后台按环境在线登记应用，注册客户端只发生在接入配置阶段。

**成功判据**　同一老用户分别用原手机号和万联登录，Mio 返回同一个 `userId`，打开同一个原有项目或资产。首次使用者自己决定账号归属。

## 3. 依据及当前系统

- **万联文档。**《接入router测试环境登录功能》定义了 Router 的加密跳转、成功及拒绝回调、客户端注册和刷新。《desk-router登录》给出兼容的 JavaScript 加密示例。`register` 定义应用身份，日常登录通过 `/authorize?enc=…` 发起。
- **2026-11-24 测试环境实测。** 请求使用 `clientName="miioo"`、展示名 `Miioo` 和 `clientType="web"`。用户同意后，测试浏览器在本机接到 `access_token`、`refresh_token`。应用访问令牌解码得到 `client_id="miiooClientId"`，其字符串 `sub` 与同次 Router 用户资料中的 `userId` 一致。Router 自己登录时得到的 `routerClientId` 属于中间步骤。样本未包含手机号声明，勾选授权手机号也不能替代 Mio 的手机号验证。
- **实测范围。** 此次完成了万联授权与浏览器回调。小写客户端的注册成功回包、Mio 后端验真和会话签发、跨次主体稳定性、生产配置仍待验证。换令牌请求 `swapToken` 只取到 HTTP 200 与响应头，最终令牌参数由独立的浏览器回调记录确认。样例 Java `AuthorizationFilter` 会校验签名、读取 `sub` 与 `client_id`，并查询万联的令牌状态。实测 `getUserInfo` 使用的是 Router 会话。
- **Mio 基线。** Better Auth 已管理 `user`、`account`、会话 Cookie 和禁用账号。手机号可空且唯一。现有手机号验证码登录遇到新号码会自助建号。已登录用户的手机号绑定要求近期会话和空闲号码。现有通用社交登录入口只开放微信，万联需要新增明确的入口。[认证底座](../../auth.md) · [认证 HTTP 契约](../../apis/auth.md) · [已接受的手机与微信能力](../ai-drama-foundation/complete/report.md#phone-wechat-auth)
- **前端基线。** miioo 的 `frontend/src/api/auth.js` 仍使用旧版手机号登录接口和返回的 token。新 Mio 的身份读取使用 HttpOnly Cookie。mio-admin-web 的“全局设置”已承载邮箱与短信策略，有独立管理员会话。用户端会话和管理端权限都需接回各自现行契约。[管理端契约](../../apis/admin.md) · [已接受的后台全局配置](../web-admin-console/complete/report.md#admin-global-settings)

## 4. 产品目标与范围

本期交付按环境注册客户端、万联 Web 登录、首次账号选择、已有手机号账号绑定、个人中心显式绑定，以及原有手机号登录的兼容。这里的“绑定已有账号”只增加该账号的登录方式。两个已存在的 Mio 用户之间的人员或资产合并另行处理。

上线验收须取得三类结果。第一，表中四条用户路径都能从实际入口走到预期的 Mio 身份。第二，重复提交、绑定冲突、拒绝和无效令牌产生的额外人员或跨用户关联数均为零。第三，管理员刷新页面后可查到经核对的登记状态，普通用户无法执行登记。具体观察方法见第 8 节。

本期把万联授权用于登录。Mio 会话采用现行期限与撤销机制，登录本身无需长期保存万联令牌。若未来业务需要持续代用户访问万联，再单独评审刷新、撤销联动与令牌保管。原文档给出的非 30 天免登录模式为访问令牌 2 小时、刷新令牌 24 小时。选择 30 天免登录后不支持续期。刷新接口只列 `router`、`desk` 两种 `clientType`，Miioo 的取值须由万联确认。这项未决只影响后续续期能力。

## 6. 人员与绑定数据

Mio 的 `user.id` 是人员和业务资源的归属键。拟在 Better Auth 的 `account` 中新增 `providerId="onelink"` 的记录，`userId` 指向该人员。`accountId` 用验证通过的签发方、应用 `client_id` 和字符串 `sub` 按无歧义的固定格式构造。测试和生产分别配置与存储。若万联调整主体命名或更换客户端，先核对旧绑定映射再切换。

| 数据                 | 用途与约束                                                                                                                                                                                                                                        |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 应用登记             | 按环境记录 `clientName`、已核对的 `clientId`、登记状态、来源、操作者和时间。SSO 的 AES 加密材料与令牌验真配置走服务端私有配置。                                                                                                                   |
| 人员与第三方账号     | 复用 `(providerId, accountId)`、`(userId, providerId)` 两项唯一约束。新用户走现有建人逻辑并分配 `displayId`。未验证手机号留空。认证库需要邮箱时，沿用保留域生成未验证占位邮箱。昵称、手机号文本、实名信息和令牌都不承担关联键的职责。             |
| 一次授权和待选择身份 | 服务端保存用途、浏览器关联、有效期、消费状态。绑定另关联发起时的 Mio 用户与会话。验证成功但尚未选账号时只暂存已验证主体，浏览器持有短时 HttpOnly 凭据。到期、取消或完成后失效。                                                                   |
| 事务与重试           | 新建人员和万联关联同事务提交。绑定已有人员时原子检查归属、写关联并消费待处理操作。唯一约束冲突后核对现有归属。同一已完成操作重试可显示既有结果，跨账号冲突不覆盖。身份写入成功后才签发 Mio 会话。若响应丢失，用户可重新授权进入已建立的同一账号。 |

## 7. 功能与接口实施

下述路由名称与返回体供前后端评审。实现时将采用的契约同步至认证和管理 API 规范。后端改动分别归入[认证路由](../../../src/auth/http.ts)、[短信验证](../../../src/auth/phone.ts)、[用户资料](../../../src/auth/account.ts)和[管理路由](../../../src/admin/http.ts)。用户端改造 miioo 的 `LoginModal.jsx`、`ProfileModal.jsx` 和认证 API 适配。管理端在 mio-admin-web 的 `GlobalSettingsPage.tsx` 增加登记区。

### 7.1 管理员在线注册

在 **全局设置 → 登录方式 → 万联登录** 显示当前环境、`miioo`、登记 ID 与状态，提供独立「注册万联客户端」按钮。页面打开仅读取状态。由管理员明确点击发起一次请求，执行中禁用重复提交。Mio 后端校验管理员 Cookie 和允许的 Origin 后调用当前环境固定的万联地址。测试环境为 `POST https://api-test.wanlian.cloud/sso/client/register`，JSON 请求体为 `{"clientName":"miioo"}`。文档限制名称最多 50 个字符且不含空格。注册接口返回的应用 ID 用于检查回调令牌归属，授权跳转参数使用登记名称。

| 万联结果                                      | 后端行为及管理员反馈                                                                                                                                                       |
| --------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| HTTP 成功且业务码 `200`                       | 核对返回名称、非空 `data.clientId`，保存登记，显示「已注册」及 ID。仅能确认应用已登记，正式启用登录另验回调。                                                              |
| `362` 已存在                                  | 本地有同环境可信登记时展示既有信息。没有可信 ID 时显示「万联已存在，待核对 ID」，由管理员依据万联确认值补录并写审计。保留原值，避免根据名称拼接 ID 或取用 Router 中间 ID。 |
| `363`、`364`                                  | 对应提示名称含空格、万联客户端模板缺失。管理员可用返回的 `traceId` 定位。                                                                                                  |
| 超时、HTTP/业务错误、响应缺字段、本地保存失败 | 显示「登记结果待核对」或具体错误，保留可用登记。如远端已成功、本地未保存，按已存在流程恢复。日志只保留操作、环境、业务码与追踪标识。                                       |

### 7.2 发起授权与验证回调

1. 前端调用 Mio 发起接口。后端区分匿名登录与登录后绑定，根据服务端环境配置取产品站点和固定 HTTPS 回调，将本次操作关联到发起浏览器。绑定沿用现有近期会话规则（10 分钟），记录 `userId` 和 `sessionId`。
2. 后端生成 `clientType="web"`、`clientName="miioo"`、`name="Miioo"`、`url`（站点 origin）、`callback`、`timestamp`（毫秒）。按供应商格式对 JSON 做 AES-256-GCM 加密。密钥按原示例取 32 个字符、不足补字符 `0` 后用 UTF-8 编码。12 字节随机 IV，16 字节标签。分别 Base64 编码为 `iv:authTag:ciphertext`，整体 URL 编码后返回授权地址。测试入口为 `https://scenic.wanlian.cloud/authorize?enc=…`。用户端只打开该地址。
3. 万联处理用户登录与同意，浏览器导航到 Mio 回调。后端必须把本次返回和原浏览器的一次操作配对。`state` 或等价的万联支持机制须先联调确认。样本没有回传 Mio 的 `state`，Router 内部的 `state` 不能代用。拒绝时按 `unauthorized=true` 结束。缺少关键参数、过期、来自其他浏览器或重复回调均不能建立新身份关联。[重定向流程保护](https://www.rfc-editor.org/rfc/rfc9700.html#section-2.1)
4. 通过万联认可的第三方验证接口，或按其正式签发、验签及有效状态契约，确认访问令牌真实有效，检查签发方、受众、有效时间、应用 `client_id` 与非空 `sub`。样本的 HS256 只说明当次算法。验真参数须来自可信环境配置。`enc` 加密密钥与 JWT 验签材料各有用途。万联若要求令牌在线有效，还须验证相应状态。服务端无法确认时终止本次登录。
5. 先按用途分流。登录时，已关联且可用的用户取得 Mio 会话，未关联的用户进入账号选择页。个人中心绑定时重新核对原用户和原会话。同一身份已绑本人就显示已绑定，已归属他人则返回冲突，原用户的会话身份不切换。后端通过 303 跳转干净的本站路径，响应禁缓存并抑制 Referer。网关、应用日志和埋点略去回调查询串，前端不持有上游令牌。Router 的中间登录和换令牌请求由其自己的页面完成。

### 7.3 手机号验证与前端契约

已有账号分支在验证短信后，按规范化手机号查找**已存在、已验证且可用**的 Mio 用户。复用短信预算、限流和单次消费逻辑。为此次待绑定操作使用独立用途的挑战，绑定手机号、浏览器和操作。现有匿名 `phone-number/verify` 会自动建号，不能直接完成这一分支。实际手机号归属须有真实短信证明。测试固定码模式不能用于这次永久绑定。验证前的发码反馈避免暴露号码是否已注册。

| 入口                                                                       | 调用方、输入与成功结果                                                                                                                                                               |
| -------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `GET /api/v1/admin/onelink/sso`、`POST /api/v1/admin/onelink/sso/register` | 管理端读状态或触发一次登记。待核对已有 ID 时，可用管理员专属的补录操作，校验环境并记录依据。具体路径在此单元 C0 确定。                                                               |
| `POST /api/auth/onelink/start`                                             | 用户端传 `intent=login` 或 `bind`。成功返回 `{url}` 并建立短时浏览器关联，账号身份取自服务端。                                                                                       |
| `GET /api/auth/callback/onelink`                                           | 浏览器从万联导航。后端消费经核对的操作，验证令牌，跳转到已登录、待选择、取消或失败页面。                                                                                             |
| `POST /api/auth/onelink/existing/send-otp`                                 | 待选择用户传 `phoneNumber`，按关联操作发送已有账号绑定用途的验证码。                                                                                                                 |
| `POST /api/auth/onelink/complete`                                          | `action=create` 明确创建新用户。`action=link_existing` 带 `phoneNumber,code` 绑定已有用户。后端读取暂存主体，核对用途和归属后签发 Mio Cookie。前端不提交目标 `userId` 或万联 `sub`。 |
| `GET /api/v1/me`、`GET /api/v1/me/profile`                                 | 沿用本站会话读取身份。资料增加只读 `onelinkBound`，个人中心据此展示状态。新用户补绑空闲手机号沿用 `/api/auth/phone-binding/send-otp` 和 `/api/auth/phone-binding/confirm`。          |

用户端沿用同站部署和 `credentials: 'include'`。首次接通后以 `/api/v1/me` 校验会话，再加载当前用户数据。拒绝、过期、重新登录、占用冲突、供应商暂不可用分别有可执行的页面提示。失败不会显示已绑定或开始加载他人资料。

### 8.3 端到端验收清单

| 场景                                         | 必须观察的结果                                                                                                                                                                 |
| -------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 后台首次注册或恢复已有登记                   | 正确的业务码、页面状态和可信 ID 对应。重复操作不会覆盖其他环境或已有 ID。普通用户调用被拒绝。                                                                                  |
| 已有手机号用户首次关联、再次登录             | 两种方式登录后，`GET /api/v1/me` 返回同一个 `userId`，并能读取一个原有项目或资产。另测输入新号码，已有账号分支产生的新人员数为零。                                             |
| 新用户创建并补绑手机号                       | 回调后选创建才产生一个人员和一个关联。可跳过绑定。用空闲手机号完成 Mio 真实验证码绑定后，两种登录方式进入同一用户。已占用号码保持原归属。                                      |
| 已登录用户从个人中心绑定                     | 发起和回调均为同一近期会话才完成。回调前退出或换账号则拒绝。查询状态与数据库归属对应。                                                                                         |
| 相同主体并发、已被他人占用                   | 并发创建最多得到一组人员与关联。两人争用同一身份只产生一个归属，失败一方保留原账号。                                                                                           |
| 拒绝、过期、禁用、失效、错误客户端或重复回调 | 登录或绑定的失败不产生新用户、关联或新会话。原有账号数据可正常核对。                                                                                                           |
| 发布环境与敏感数据                           | 固定域名能接回授权，跳转后地址干净。检查回调链路的反向代理日志、应用日志和埋点，无令牌、验证码、密钥或完整手机号。用户端存储不含万联令牌。旧手机号、微信及管理员登录回归通过。 |

业务验收记录环境、测试场景、脱敏结果和实际候选。协议替身覆盖异常与并发。万联测试环境与真实浏览器覆盖同意、拒绝和账号归属。若生产域名、验真材料或老用户迁移条件尚未落实，记录对应的未验范围并保留原登录入口。
